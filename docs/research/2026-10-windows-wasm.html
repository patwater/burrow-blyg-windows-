Burrow on Windows and in the browser

Research on the studio-0.32 worktree, 2026-10-06. Toolchain 1.98.1, gpui-kit 0.6.6 → gpui-pre 0.3.6 (Zed snapshot bcf6582).

verified I ran it or read it in source. inference My judgement or extrapolation. Effort: small under 2 days, medium about 1 week, large several weeks.

1. Windows: feasible. GPUI already supports it; our own macOS code is the work.

The UI framework is ready. Most of the work is in Burrow's three WebKit surfaces, the updater, and packaging.

GPUI's Windows backend

verified The pinned GPUI ships a Windows backend

gpui-pre-platform selects gpui-pre-windows under cfg(target_os="windows"). It is 12,769 lines of Rust: DirectX 11 renderer, DirectWrite text, IME, clipboard, dialogs, credentials, notifications. For comparison, the macOS backend is 10,853 lines.

verified Zed ships it as stable

Zed 1.0 (2026-04-29) ships stable on Windows, Linux and macOS. Sources: zed.dev/blog/zed-1-0, linuxiac, and earlier friction in The Register, 2025-08.

verified Release builds need fxc.exe

gpui-pre-windows/build.rs compiles the HLSL shaders with fxc.exe in non-debug builds, and gpui-pre/build.rs embeds a manifest with llvm-rc/rc.exe. Plan release builds on a windows-latest CI runner, not a cross build from the Mac.

2. WASM / browser: possible, with real costs. First decide what it's for.

Does GPUI run on the web?

verified Yes, and it's already in our lockfile

gpui-pre-web 0.3.6 (Zed's gpui_web, 6,949 lines) is selected for cfg(target_family="wasm") by both gpui-pre-platform and gpui-kit. Its header comment: "one document-owned canvas … supports one top-level window. Browser WebGPU is preferred by default, with an automatic WebGL2 fallback."

verified Upstream history

The initial implementation is zed#50228 "GPUI on the web", merged 2026-02-26: "a basic web platform for the wasm32-unknown-unknown target." Since then: a fetch HTTP client (#50463, 2026-03-02), IME (#50437), and iOS keyboard fixes (#64882, 2026-09-28). There are 57 commits to crates/gpui_web. Latest snapshot: gpui-pre-web 0.3.8 (2026-10-05). Zed itself doesn't ship a web build.

verified Gaps in WebPlatform (platform.rs)

prompt_for_paths / prompt_for_new_path: "not supported on the web". write/read_credentials: Err. reveal_path / set_menus: no-ops. quit: unsupported. There's one window, and reopening it is an error. The default multithreaded feature uses wasm_thread. inference That needs SharedArrayBuffer, which needs COOP/COEP cross-origin isolation headers from the host.

Options

(a) GPUI on the web large

Reuses: the whole GPUI UI (60.8k lines in blyg-app), theming, keymap, VMs.
Costs: the core in a Worker or async rewrite. There's no WebView in a canvas, so the reader, preview and browser pane (all WKWebView today) need DOM overlays layered above the canvas. Spellcheck, file dialogs, credentials and menus all go. A COOP/COEP host is needed for threads.
Lost: canvas text has no native find-in-page, screen reader access or browser text selection. Larger download (wgpu + app, multiple MB). inference The backend is 7 months old and Zed doesn't ship on it. Expect rough edges.

(b) Rust core in wasm + web UI large

Reuses: blyg-render as is (verified), model/tk/wire types, SQL schema and queries through rusqlite on sqlite-wasm-rs + OPFS, and sync logic once HTTP is abstracted.
New: the entire UI (Leptos/Dioxus, or TS + wasm-bindgen). It's a second UI to maintain alongside GPUI.
Kept: NV-speed local search and offline outbox (OPFS SQLite is fast). Bearer tokens + CORS and OAuth PKCE in studio 0.28+ fit a browser client.
Lost: local CLI AI, global hotkey, native spellcheck (the browser's own is fine), and the ad-blocking pane (the browser does that).

(c) PWA served alongside the blyg medium on top of (b)

Same as (b), packaged as an installable PWA from the blyg's own origin (or a static host). Same-origin removes CORS and token-paste friction, gives an offline service worker, and works on phones. It needs a Worker route or static asset upload on the blyg, which is maintainer-side (a Worker patch needs explicit go-ahead).

(d) Tauri for Windows + web build sharing one UI very large

Effectively a rewrite of blyg-app into HTML/JS. The core goes behind Tauri commands, and the same UI ships to the web. It gives up GPUI's NV-speed native feel, which is Burrow's reason to exist, and it duplicates what the GPUI Windows port gets for medium cost. inference Not recommended.

What would a browser Burrow offer that Studio doesn't?

inference Studio (the upstream SPA) already covers writing, TK, publishing, versions, subscriptions and settings, and it's always online. A browser Burrow would add:

  • Local-first and offline. Your posts and imported reading live in OPFS SQLite, edits queue in an outbox, and nothing waits on the network.
  • Notational-Velocity search across your own posts and everything you read, done locally with FTS5.
  • The reader: stream / three-pane reader, lineage glyphs, one entry per post with edit diffs, read-state sync, quote picker from held posts.
  • Multiple blygs and profiles in one client, plus scratch notes and capture.
  • Bring-your-own AI provider (subject to CORS), where Studio uses the server's generator.

If the reader and offline aren't what the user wants on the web, Studio already covers the authoring case, and a browser Burrow mostly duplicates it.

3. Recommendation

do Windows: port the GPUI app

Order: (1) gate objc2 and the unix updater bits, add keyring/windows-native, Windows paths, and secondary- keys. Add a windows-latest CI cargo check/test job so it stays green. (2) WebView2 preview/reader through wry. (3) Updater and packaging. (4) Browser-pane blocking and spellcheck last; until then, links can open in the default browser.

cheap prep Keep the web door open

Add a CI cargo check --target wasm32-unknown-unknown -p blyg-render job; it already passes. When convenient, split the pure parts of blyg-core (model, tk, wire types) from IO so they also build for wasm. These are small steps that don't commit to a web UI.

defer A browser Burrow

Only worth it if the reader, offline use or phones matter on the web. In that case, go with (b)/(c): core in a Worker, OPFS SQLite through rusqlite + sqlite-wasm-rs, fetch-based API, a thin DOM UI, served from the blyg. Revisit (a) GPUI-web in about 6 months, once WebViews-over-canvas and accessibility are solved upstream.

Method notes

  • I installed only the rustup std components x86_64-pc-windows-msvc and x86_64-pc-windows-gnu; wasm32-unknown-unknown was already installed. I didn't install cargo-xwin, mingw, zig or the MSVC SDK.
  • The stub C compiler, archiver and llvm-rc live in the scratchpad (stub/, wincheck.sh, wasmcheck.sh), and builds went to scratchpad/tgt. The temporary manifest edits (objc2 gating, getrandom/js) and Cargo.lock were restored. The worktree is clean.
